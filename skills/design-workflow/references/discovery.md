# Discovery — методика сбора фактуры для режимов N и G

Режимы N и G не имеют live-DOM проектируемого экрана. Фактура берётся из четырёх источников, в порядке достоверности: **код и действующие правила → владелец → проектные документы → референсы**. Источник оценивается по актуальности и полноте; противоречия фиксируются явно.

## 1. Источники

### Бэкенд/код (самый надёжный)
- Сущности и поля, которые реально есть в API/БД — что можно показать и редактировать.
- Статусные машины (какие статусы реально поддерживаются; устаревшие статусы не выдавать за действующие).
- Guard'ы и лимиты на бэкенде (например, лимит операций или обязательное заполнение профиля; значения брать из текущего продукта) — они должны стать видимыми в UI.
- Если кода под рукой нет — запросить у владельца список полей/эндпоинтов, не угадывать.

### Владелец (интервью, 5–7 вопросов)
- Зачем пользователь открывает этот раздел? Что делает после? (job-to-be-done)
- Что пользователь делает руками, что должен делать продукт? (кандидаты на автоматизацию — Tesler)
- Какая частота: раз в день, раз в неделю, раз при онбординге? (ритм → размещение)
- Что случится, если пользователь этого не сделает? (вес блока)
- Чего НЕ должно быть видно обычному пользователю? (админ-механики, очереди)
- Есть ли существующие данные/цифры для демо? (или всё помечаем демо-плейсхолдерами)

### Референсы (снимаем, не фантазируем)
- Аналоги: открыть в agent-browser, `screenshot`, разобрать композицию (не копировать стиль, если продукт другой).
- Скриншоты чужих решений вставлять в артефакт-отчёт только как сравнение паттернов.

### Документы
- Читать доступные проектные документы, PRD и журнал решений. Сверять актуальность с кодом и владельцем. Специальный инструмент памяти не требуется; неподтверждённые старые решения помечать как гипотезы.

## 2. Модель данных и состояний (выход Discovery)

Таблица на каждый блок будущего раздела:

| Блок | Данные (источник) | Действия пользователя | Состояния |
|---|---|---|---|
| Пример: Очередь вопросов | вопросы работодателей (API) | ответить / отложить / повторить | пусто / список / загрузка / ошибка сети / частичные данные |

Правила состояний:
- **Empty** — не пустой прямоугольник, а объяснение + следующее действие («Всё разобрано — очередь пуста»).
- **Loading** — скелетоны, не спиннеры посреди страницы.
- **Error** — что пользователь может сделать (повторить / проверить подключение), а не «что-то пошло не так».
- **Частичные данные** — что показывать, если поля нет (placeholder ≠ выдуманное значение).

## 3. Классификация по ролям (та же, что в R-инвентаре)

- **Данные** (set once) / **Правила** (тюнятся) / **Каналы-инфра** / **Не настройки** (очереди, админ).
- Для G это же делается на уровне всего продукта: какие разделы вообще нужны, какой ритм у каждого.

## 4. Проекционный чеклист (эвристики ДО экрана)

При проектировании прогонять макет по списку — это те же эвристики, перевёрнутые из аудита в требования:

- [ ] У каждого числового/выборного контрола есть лейбл и словесное последствие (H4)
- [ ] Деструктивные действия: подтверждение или undo (H2/H5)
- [ ] Guard'ы бэкенда видимы: чеклист требований у тумблера, счётчики лимитов (H4)
- [ ] Статус сохранения/применения на каждое изменение (H4, Peak-End)
- [ ] Поиск/навигация, если блоков >7 (H6/H7, Hick)
- [ ] Данные-производные помечены источником, есть кнопка регенерации (Tesler, зависимости)
- [ ] Смысловых групп ≤4, ритмы (set once vs тюнится) не смешаны (Gestalt, H8)
- [ ] Тап-зоны ≥44px на мобиле (Fitts)
- [ ] Один акцентный цвет только на первичных действиях (H8)
- [ ] Empty/loading/error продуманы для каждого блока (H9)

## 5. Ловушки

- Не переносить домыслы из прошлых сессий без подтверждения владельцем.
- «Сабтайтл обещает больше, чем есть» — проверять данные, не подписи.
- Референс-залипание: аналог решает свою задачу со своими данными; переносить паттерн, а не композицию целиком.
- Для G: не проектировать дизайн-систему до 2–3 утверждённых экранов — компоненты вытаскиваются из прототипов, не придумываются.
